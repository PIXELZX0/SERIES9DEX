# Series9DEX — 설계 명세서

> **프로젝트:** Series9 Decentralized Exchange
> **위치:** `series9/Series9DEX/`
> **상태:** 초안 (Draft v0.9)

---

## 1. 개요 (Overview)

**Series9DEX**는 **두 ERC-20 토큰** 간의 탈중앙화 거래소(DEX)입니다. 페어의 양쪽 토큰 모두 **어떤 ERC-20** 이든 자유롭게 조합할 수 있습니다 (**ANY/ANY 페어**). **SER9 또한 ERC-20 (또는 그 래퍼)** 이므로 페어의 한쪽 토큰으로 자연스럽게 참여할 수 있으며, 반대로 SER9 없이 다른 ERC-20 끼리의 페어도 문제없이 생성·운영됩니다.

AMM 기반의 시장가 주문과, **완전 온체인 오더북(on-chain orderbook)** 기반의 지정가 주문을 모두 지원합니다.

모든 거래 페어는 고유한 **Pair ID** 로 식별되며, 해당 ID 는 페어에 속한 **풀(Pool)** 을 조회·연결하는 키로 사용됩니다.
**수수료(fee rate)는 풀을 생성하는 사람이 직접 선택**할 수 있어, 같은 페어라 하더라도 풀마다 다른 수수료 정책을 운영할 수 있습니다.
풀 생성자가 설정한 lpFee 의 **0.1% 는 프로토콜 수수료**로 회수되며, 나머지 99.9% 는 풀의 LP 등에게 분배됩니다.

## 2. 핵심 구조 (Core Architecture)

```
Series9DEX
├── DexRegistry (UUPS, 타임락 소유)  ── 페어 등록 + 팩토리 배선 + 비상 정지
│     ├── createPair(tokenX, tokenY) ──CREATE2──→ Pair (팩토리를 배포 시점 값으로 고정)
│     └── poolToPair / isSpotPool  ── 주변부용 풀 진위 확인
│
├── Pair (페어당 1개 컨트랙트, 주소 = 페어 식별자)
│   ├── 온체인 오더북  ── ALL ON-CHAIN
│   │     ├── bidLevels / askLevels  (가격 정렬 연결 리스트 + FIFO)
│   │     └── 매칭: 현물 풀 ↔ 반대편 호가, 한계가격이 나은 쪽부터
│   │
│   ├── Spot Pool (현물 풀, 수수료율당 1개)
│   │     ├── token0 / token1 reserves
│   │     ├── lpFeeRate  (정규 티어 4개 + 커스텀 12슬롯)
│   │     ├── 누적가격 오라클 + 에포크 관측 기록  ──→ 선물 풀의 마크 가격
│   │     └── protocol cut = lpFeeRate × 0.1% → ProtocolTreasury
│   │         LP share    = lpFeeRate × 99.9% → LP
│   │
│   └── Perp Pool (선물 풀, 무기한)
│         ├── Long / Short positions  ── 요청 → 정산 2단계 (§5.2.1)
│         ├── 단측 LP 금고 (quoteToken) ── 모든 포지션의 상대방 (예치·인출도 2단계)
│         └── 펀딩 · 청산 (보상 하한 있음)
│
├── DexRouter  ── 멀티홉 스왑 + deadline (무상태 · 무권한)
│
├── DexPositionManager (ERC-721)  ── LP 포지션 소유권
│     ├── 풀의 지분을 수탁
│     └── tokenId ──→ {pool, isSpot, liquidity}
│
└── ProtocolTreasury (UUPS)  ── 프로토콜 수수료 금고 (타임락 소유)
```

## 3. 페어 (Pairs)

### 3.1 페어 구성
- 모든 페어는 **두 ERC-20 토큰**의 조합으로 구성됩니다 (**ANY/ANY 페어 지원**).
- **SER9** 도 ERC-20 (또는 그 래퍼) 이므로 페어의 **어느 한쪽**이든 자유롭게 참여할 수 있고, **SER9 없이** 다른 ERC-20 끼리의 페어(예: `USDC / WETH`) 도 제약 없이 생성할 수 있습니다.
- 두 토큰의 주소가 동일할 수 없습니다 (셀프 페어 금지).
- 예시:
  - `SER9 / USDC`
  - `SER9 / WETH`
  - `USDC / WETH`
  - `WBTC / USDC`
  - `SER9 / 프로젝트 토큰 X`

### 3.2 페어 식별자
- 페어의 식별자는 **`Pair` 컨트랙트 주소 그 자체**입니다. 별도의 `bytes32 pairId` 는 없습니다.
- `DexRegistry.createPair(tokenX, tokenY)` 가 `Pair` 를 **CREATE2** 로 배포하며, salt 는 정렬된 두 토큰 주소의 keccak256 입니다. 정규화 덕분에 `WETH/USDC` 와 `USDC/WETH` 가 같은 주소로 수렴해 중복 생성이 방지됩니다 (`PairAlreadyExists`).
- 주소가 결정적이므로 배포 전에도 오프체인에서 계산할 수 있습니다: `DexRegistry.predictPairAddress(tokenX, tokenY)`.
- 정렬은 `PairKey.sort` 가 담당합니다 — `token0 < token1`, 동일 토큰·영주소는 거부.

```
// salt 로만 쓰이는 값. 페어를 가리키는 식별자가 아닙니다.
salt = keccak256(abi.encodePacked(token0, token1))
pair = CREATE2(DexRegistry, salt, Pair(registry, token0, token1))
```

> 참고: 수수료율은 salt 에 들어가지 않습니다. 같은 페어가 **풀마다 다른 수수료**를 갖기 때문입니다 (§6).

### 3.3 페어 ↔ 풀 매핑
- 하나의 `Pair` 가 **여러 풀**을 소유합니다.
  - 현물 풀: **수수료율당 1개**. 정규 티어 4개 + 커스텀 12슬롯 (§6.1)
  - 선물 풀: quoteToken × 수수료율 조합당 1개. 무기한(perpetual) 이므로 만기별 구분은 없습니다
- 조회: `Pair.spotPools(i)` / `spotPoolsLength()`, `Pair.perpPools(i)` / `perpPoolsLength()`.
- 역방향 조회는 레지스트리가 제공합니다: `DexRegistry.poolToPair(pool)`, `isSpotPool(pool)`. 주변부 컨트랙트가 "이 주소가 정말 우리 풀인가" 를 확인하는 경로입니다.

## 4. 주문 유형 (Order Types)

### 4.1 시장가 주문 (Market Order)
- AMM 의 현재 호가(현물 풀 reserves 기반)로 즉시 체결.
- 슬리피지 허용치(`minAmountOut`) 지정 필수.
- 라우팅 경로는 **호출자가 지정**합니다. `DexRouter.swapExactTokensForTokens(pools, tokenIn, amountIn, minAmountOut, to, deadline)` 에 홉마다 쓸 풀 주소를 배열로 넘깁니다 (Uniswap V3 방식). 어느 수수료 티어를 쓸지는 오프체인 판단이며, 온체인에서 풀을 훑는 루프를 스왑 경로에 넣지 않기 위한 선택입니다.
- 각 홉은 `DexRegistry.isSpotPool` 로 검증한 뒤에만 approve 합니다. 라우터는 무상태·무권한이며 호출 사이에 잔고를 들고 있지 않습니다.
- 견적: `quoteExactInput` / `quoteExactOutput`.
- 풀을 직접 호출해도 됩니다 (`SpotPool.swapExactIn`). 그 경우 deadline 이 없습니다.
- 수수료는 **해당 풀의 `lpFeeRate`** 이며, 그 안에서 0.1% 가 프로토콜 몫입니다 (§6).

### 4.2 지정가 주문 (Limit Order) — 전량 온체인
- 원하는 가격에 도달했을 때 자동 체결.
- **호가창 자체가 온체인에 저장·관리**됩니다. 오프체인 relayer 를 두지 않으며, 외부 운영 주체 없이 누구나 체인만 보고 호가를 조회·체결할 수 있습니다.
- 호가창은 `Pair` 컨트랙트가 직접 들고 있습니다. 별도 `Orderbook` 싱글턴이나 `bytes32 pairId` 는 없으며, `Pair` 주소 자체가 페어 식별자입니다.

#### 온체인 오더북 구조
```
Pair (페어당 1개 컨트랙트)
├── bidLevels[price]   ── 매수 레벨 (FIFO 주문 연결 리스트 + totalBase)
├── askLevels[price]   ── 매도 레벨
└── bestBidPrice / bestAskPrice ── 가격 정렬 연결 리스트의 헤드
```
- 가격은 **raw quote 단위 / raw base 단위 × 1e36** (`priceX36`) 입니다. 1e18 스케일에서는
  18자리 밈코인/6자리 스테이블($0.00001, raw 1e-17)이 `10` 으로 읽혀 한 칸이 10% 였고,
  raw 1e-18 미만은 0 이었습니다. 1e36 이면 raw 1e-30 까지 유효숫자 6자리가 남습니다.
- 가격 단위는 **유효숫자 6자리 십진 그리드**로 고정됩니다 (`MAX_PRICE_SIG_DIGITS`).
  페어별 `tickSize` 설정값이 아니라 가격의 순수 함수라, 선착순으로 고정되는 값이
  없고 토큰 데시멀 차이가 큰 페어도 그대로 커버됩니다.
  `Pair.priceIsValid(priceX36)` / `Pair.tickSizeAt(priceX36)` 로 조회합니다.
- 가격 상한 `MAX_PRICE_X36 = 1e72`, 수량·매수 에스크로 상한 `uint128`. 매칭 산술은 전부
  512비트 중간값(`mulDiv`)이라, 1 wei 짜리 극단 가격 주문으로 교차 판정을 오버플로시켜
  페어 전체 매칭을 멈추는 일이 없습니다.
- 최소 주문 금액은 **quote 토큰 1e-4 개** (`minQuoteNotional`, quote 의 `decimals()` 기준,
  읽을 수 없으면 18). 고정 raw 값은 18자리 토큰엔 무의미하고 2자리 토큰엔 과했습니다.
- 주문 등록/취소/매칭 모두 트랜잭션으로 발생 — 가스 비용 발생.
- 호가 조회: `Pair.bestBid()` / `bestAsk()` (최우선 호가),
  `Pair.levels(side, startPrice, count)` (depth, 페이지네이션).
- 주문 조회: `Pair.ordersOfLength(maker)` / `Pair.orderIdsOf(maker, start, count)` (id 목록, 상세는 `orders(id)`).
- 매칭 진입점: `Pair.placeOrder` (등록 즉시 `PLACE_MATCH_FILLS` 만큼 매칭), `Pair.matchOrders(maxFills)` (누구나) 와 `Pair.matchFromPool(maxFills)` (현물 풀이 자기 스왑 직후 호출). `maxFills` 는 풀 hop 수 · 직접 체결 횟수를 제한하고, 취소·만료 노드 정리는 별도 예산(`maxFills × POPS_PER_FILL`)을 씁니다. 같은 예산을 쓰던 때는 취소 주문으로 채운 레벨이 새 주문의 등록 매칭 예산을 다 먹어, 체결 가능한 주문이 그대로 쉬게(=샌드위치 가능) 만들 수 있었습니다.

##### 등록 즉시 매칭
주문은 등록되는 트랜잭션 안에서 바로 풀·호가와 매칭되고, 남은 부분만 호가창에 쉽니다.
체결 가능한 지정가가 그냥 쉬고 있으면 아무나 풀 가격을 그 지정가까지 밀어 올린 뒤 스왑 훅으로
체결시키고 되파는 **단일 트랜잭션 샌드위치**가 가능했습니다 (5.0 지정가 매수가 깊은 4.0 풀에서
4.05 대신 4.97 에 체결). 즉시 매칭이 §4.2 의 "풀에서 오는 가격 개선"을 실제로 보장합니다.

##### 더스트와 지급 실패
- 남은 수량이 자기 지정가에서 quote 1 단위도 안 되는 주문은 매칭이 닿는 순간 **닫고 환불**합니다
  (`FILLED` 처리). 예전엔 교차된 호가 맨 앞의 더스트 하나가 메이커가 취소할 때까지 뒤의 모든 체결을 막았습니다.
- 풀에는 여유가 있는데 잔량이 지정가를 못 맞추는 주문도, 잔량이 base 또는 (그 가격의) quote 로
  `DUST_UNITS`(1e4 원시 단위) 미만이면 같은 방식으로 닫습니다 (예: WBTC 1 sat). 풀은 실효 입력과 출력을 각각
  최대 1 단위 내림하므로 이보다 작은 잔량은 1bp 넘게 잃어 영영 못 맞출 수 있고, "건널 풀이 없음"으로 읽히면
  그 쪽 전체를 멈추고 체결 가능한 주문을 쉬게 만들어 샌드위치를 되살립니다. 그보다 큰 주문은 풀이 지정가와
  자기 충격을 몇 bp 지나면 체결되므로 실패는 "풀이 아직 지정가에 있음"으로 읽고 **닫지 않고 기다립니다**.
  풀 여유 대비 크기로 판단하던 때는 풀을 딱 맞는 거리로 밀어 정상 주문도 닫을 수 있었습니다
  (2차 리뷰 PoC: 100 BTC 풀에서 $45 WBTC 매도가 미체결로 닫힘).
- 매칭 중 메이커에게 보내는 대금·환불이 실패하면(블랙리스트 토큰 등) 되돌리지 않고
  `claimable[메이커][토큰]` 에 적립합니다. 메이커는 `claim(token, to)` 로 **다른 주소로도** 받을 수 있습니다.
  수령 불가 메이커 한 명이 페어 전체 매칭을 멈추던 문제를 막습니다.

##### 풀을 믿지 않는 체결
풀 hop 은 페어가 직접 잔고 변화를 재서 검증합니다: 실제로 나간 양 ≤ 승인량, 들어온 양 ≥ 지정가 기준
최소 수령량. 어긋나면 그 hop 만 되돌리고(외부 자기 호출 + try/catch) 매칭은 계속됩니다. 승인은
hop 직후 0 으로 되돌립니다. 악성 풀이 섞여도 에스크로를 빼낼 수 없고, 수수료 차감 토큰처럼
풀과 맞지 않는 토큰은 풀 체결만 건너뜁니다.

##### 체결 소스 — 둘 중 한계가격이 나은 쪽
주문은 **현물 풀** 과 **반대편 호가** 양쪽에서 체결되며, 매 시점 더 유리한 쪽이 먼저 쓰입니다.

1. **풀 대조.** 이 페어의 모든 현물 풀 중 목표가에 닿기까지 여유가 가장 큰 풀을 골라 그 지점까지 소진합니다. 여유가 큰 풀부터 방문해야 주어진 hop 예산 안에서 최대한 체결됩니다.
2. **책 직접 체결.** 호가가 교차(`bestBid >= bestAsk`)해 있으면 두 주문이 서로 체결됩니다. 양쪽 에스크로가 이미 `Pair` 에 있으므로 외부 호출 없이 전송 2회, **풀 수수료 0**.

풀을 어디까지 쓸지는 **교차 중간가**(`(bestAsk + bestBid) / 2`)가 정합니다. 풀이 그보다 유리한 동안만 풀을 쓰고, 거기서부터 책이 받습니다. 그래서 주문이 더 좋은 상대를 지나쳐 풀로 가지도, 풀이 더 쌀 때 책을 잡지도 않습니다.

##### 직접 체결가 — 두 지정가의 중간값
```
execPrice = (askPriceX18 + bidPriceX18) / 2
```
- 매도자는 자기 호가 **위**에서, 매수자는 자기 지정가 **아래**에서 체결됩니다. floor 나눗셈이라 `ask ≤ mid ≤ bid` 가 보장됩니다.
- 교차 스프레드를 양쪽이 절반씩 나눠 갖습니다. **어느 쪽이 먼저 주문을 냈는지는 체결가에 영향을 주지 않습니다.**
- 대안이었던 "매수호가 체결"(매도자 수취 최대화)은 폐기했습니다. 매수자가 교차 시 항상 지정가 전액을 내게 되면 합리적 매수자는 체결 가능한 최소값으로 호가를 낮추게 되고, 그 결과 매도자가 닿을 수 있는 최우선 매수호가 자체가 내려갑니다.
- 체결가는 유효자릿수 그리드를 벗어날 수 있습니다. 그리드는 **레벨 개수**를 묶는 장치이고 체결가는 레벨을 만들지 않으므로 무해합니다.
- 매수자의 가격 개선은 풀에서 나옵니다. 풀이 주문 전량을 소화할 만큼 깊으면 평균가가 어떤 상한에도 닿기 전에 필요 수량이 채워집니다 (예: 4.0 짜리 깊은 풀에서 5.0 매수 → 4.05 체결). 등록 즉시 매칭되므로 이 개선을 실제로 받습니다.
- 두 주문이 모두 쉬고 있다가 만날 때만 중간값이 적용됩니다. 매수가 먼저 들어오면 그 시점의 풀이 가장 좋은 상대이므로 지정가 한도까지 풀에서 먼저 체결됩니다.

#### Limit Order 필드 (예시)
| 필드 | 타입 | 설명 |
|---|---|---|
| `maker` | `address` | 주문 등록자 |
| `side` | `enum (BUY / SELL)` | 매수/매도 |
| `priceX36` | `uint256` | 지정 가격 (raw quote per raw base, X36) |
| `amountBase` | `uint256` | 주문 수량 (base) |
| `filledBase` | `uint256` | 체결 누계 |
| `escrowRemaining` | `uint256` | 남은 에스크로 (SELL: base, BUY: quote) |

| `status` | `enum (OPEN / FILLED / CANCELLED / EXPIRED)` | 주문 상태 |

페어는 `Pair` 컨트랙트 주소로 식별되므로 주문에 별도 페어 필드가 없습니다.

#### 온체인 오더북의 장단점
- ✅ **장점:** 단일 진실 공급원, 검열 저항성, 투명한 호가, relayer 의존성 없음.
- ⚠️ **단점:** 주문 등록/취소/매칭 모두 가스 비용. (Monad 등 고처리량 L1 에서 완화 기대)

## 5. 풀 (Pools)

### 5.1 현물 풀 (Spot Pool)
- **AMM 기반** 유동성 풀 (Uniswap V2 스타일 상수곱).
- 같은 `Pair` 안에서 토큰 ↔ 토큰 즉시 스왑.
- 유동성 제공자(LP) 가 유동성 공급 및 fee 분배.
- LP 지분의 표현 방식은 **§5.4** 참조 — 풀은 대체가능 LP 토큰을 발행하지 않습니다.
- reserves 는 `uint112` 로 제한합니다. 누적가격(`price*CumulativeLast`, X36)이 `reserve × 1e36` 에서
  조용히 wrap 하지 않게 하기 위함입니다.
- 깊이는 **역수**로 누적합니다(`inverseLiquidityCumulativeLast`, 1e36/√(r0·r1)·초). 선물은 여기서
  √k 의 **조화평균**을 얻습니다 — 얇은 구간이 평균을 지배하므로, 창 일부에만 넣었다 빼는 유동성으로
  평균을 떠받칠 수 없습니다 (산술평균이던 때 2차 리뷰 PoC: 120초만 깊게 두고 나머지를 밀어 44.9k 지급).
- **에포크 관측 기록:** 선물 풀이 이 풀을 오라클로 쓰기 시작하면(`enableOracle`, 페어만 호출)
  에포크(`ORACLE_EPOCH = 60`초)마다 첫 업데이트 직전 상태를 한 번 기록합니다. 그 사이엔 아무 것도
  바뀌지 않았으므로 기록 하나로 그 구간 모든 경계 시각의 누적값을 정확히 복원합니다 —
  `observe(epoch, hint)`. 활발한 풀은 경계 인덱스에서 바로, 오래 쉬었던 풀은 최대 64 에포크를
  더듬거나 `hint` 로 찾습니다. 경계와 같은 초에 일어난 업데이트는 기록 쪽으로 읽으므로, 경계의
  reserves 는 **그 경계까지 유효했던 값**으로 이후 거래와 상관없이 같습니다 (예전엔 정지 해제 초의
  스왑이 정지 중 현물가로 읽혔습니다 — 2차 리뷰 PoC).

### 5.2 선물 풀 (Futures Pool)
- **레버리지 포지션** 관리 (Long / Short).
- **무기한(perpetual)** — 만기가 없습니다. 만기 정산 대신 펀딩으로 가격을 따라갑니다.
- 마진 담보는 풀의 `quoteToken` 단일. GMX 식으로 단측 LP 금고가 모든 포지션의 상대방입니다.
- 마크 가격은 연결된 현물 풀의 에포크 관측으로 계산하는 TWAP 입니다: 경계 B 의 마크 = `[B − 300초, B]` 평균 (`MARK_WINDOW`). 창이 항상 "지금 끝나는 300초" 라서 오래 쉰 풀도 며칠치 평균이 아니라 현재 가격이 마크가 되고, 누가 언제 갱신하느냐(poke)에 따라 마크가 바뀌지 않습니다.
- 가치를 옮기는 모든 동작은 **요청 → 정산 2단계** 입니다 (§5.2.1).
- 청산 보상에는 하한이 있습니다 (`LIQ_REWARD_FLOOR_BPS`, 청산 노셔널 기준). 유지증거금을 갭으로 뚫은 포지션은 남은 지분이 0이라 비율 컷만으로는 아무도 청산하지 않기 때문입니다.
- 생성 시 `maxLeverageX` 와 `maintenanceMarginBps` 는 교차 검증됩니다: 최대 레버리지의 초기증거금이 유지증거금 + 청산수수료를 넘지 못하면 거부. 안 그러면 여는 즉시 청산 가능한 풀이 만들어집니다.
- 위험 파라미터 검증은 선물 풀 생성자가 합니다 (`PerpPool.InvalidPerpParams`). 같은 (quoteToken, 오라클 풀, 수수료, 파라미터) 조합만 중복으로 거부합니다 — 수수료만으로 막으면 먼저 만든 사람이 그 수수료의 오라클·파라미터를 영구히 정했습니다.
- **오라클 깊이 상한:** 한쪽 미결제약정 노셔널(대기 중인 증가 포함) ≤ 오라클 풀 quote 쪽 깊이의 50% (`ORACLE_DEPTH_BPS`). 깊이는 최근 5분과 **최근 1시간**의 √k 조화평균(§5.1) 중 작은 값입니다. 한 창 동안만 빌려 넣은 유동성으로 큰 포지션을 열고 빼는 수법(감사 리뷰 PoC: 실제 깊이의 20배 포지션 → 청산 창에 얇은 풀을 밀어 +47.7k)을 막습니다. 그래서 새 시장은 오라클 풀에 가격이 생긴 뒤 1시간이 지나야 포지션을 받습니다. 정산 때 그 창의 깊이로 따져 미결제약정(대기 포함)이 이 상한의 **2배**(`THIN_ORACLE_BPS`)를 넘으면 — 승인 뒤 오라클이 얇아졌다는 뜻 — 창 직전 55분의 TWAP 도 최악값 범위에 넣습니다. 1시간 넘게 빌려 넣고 승인 직후 뺀 유동성 뒤의 얇은 풀을 진입·청산 창 동안 밀어도, 창 일부만 빼고 밀어도 이득이 없습니다 (2차 리뷰 PoC). 2배 여유는 상한 근처의 정직한 포지션을 위한 것입니다: 비율은 가격의 제곱근으로만 움직여 일상적인 변동으로는 걸리지 않습니다(상한과 같은 문턱이던 때는 +3% 에 걸려 1시간 가격으로 청산됨).
- 연결된 현물 풀과 같은 `Pair` 에 속합니다.

#### 5.2.1 2단계 정산
TWAP 은 현물을 늦게 따라가고, 예전 구조에선 다음 마크를 공개 1초 전에 계산할 수 있었습니다. 마크 그대로 열고 닫는 구조에서 이미 아는 가격은 LP 금고에 대한 공짜 옵션입니다 (감사 PoC: 마진 5k 로 1초 만에 +2,101). 그래서:

원칙: **요청한 뒤 요청자가 하는 어떤 행동도 결과를 바꾸지 못한다.**

| 단계 | 내용 |
|---|---|
| 요청 | `requestIncrease` / `requestDecrease` / `requestRemoveMargin`, LP 는 `requestDeposit` / `requestWithdraw`. 필요한 것(마진·예치금·지분·실행 수수료)을 에스크로. 정산 시각 `settleAt = 다음 에포크 경계 + 300초` |
| 승인 | 증가 요청은 **요청 시점에** 현재 마크·오라클 깊이·사용률 상한으로 승인되고, 그 노셔널을 결과가 날 때까지 예약합니다(`pendingLong/ShortNotional`). 실행 때 검사하면 요청자가 일부러 걸리게 만들어(자기 유동성 빼기, 다른 요청 먼저 실행) 싫어진 체결을 환불로 바꿀 수 있었습니다. 현재 마크에서 **체결 가능해야** 승인되고(허용가가 마크의 올바른 쪽, 포지션 전체에 충분한 마진), 요청 자체의 에스크로 마진이 실패 수수료 이상이어야 합니다(`MarginBelowFee`) — 일부러 실패하게 만든 요청이 용량을 공짜로 잡아 다른 거래자와 LP 출금을 막는 일을 막습니다 |
| 가격 | **요청 이후에 시작하는 첫 창**의 마크. 전부 미래 블록으로 만들어지므로 요청 시점의 정보로 이길 수 없습니다 |
| 실행 | 정산 에포크(`[settleAt, settleAt + 60초)`) 안에 **누구나** `executeOrder` / `executeLp` (실행 수수료는 실행자에게). 결과는 그 시점에 확정돼 있어 누가 실행하든 같습니다 |
| 놓치면 | 다음 창으로 **롤**. 지금까지 거친 정산 가격의 최저·최고를 기억해 요청자에게 가장 불리한 값으로 체결하고, 증가 요청은 **그 체결가에서** 건전성을 판정합니다. 반대쪽 극단에서 판정하던 때는 고레버리지 요청이 롤만으로 실패→전액 환불, 즉 가격을 본 뒤 무료 취소가 됐습니다 |
| 취소 | 포지션 요청은 **취소 불가**(예약 용량을 무료로 잡았다 놓는 그리핑 방지). LP 요청은 첫 창이 열리기 전에만, 롤된 뒤엔 불가 |
| 마진 | 요청이 대기 중인 쪽에는 `addMargin` 불가 — 대기 요청은 요청 당시 포지션으로 판정되고, 가격을 본 뒤 보충해 통과 여부를 고를 수 없게 |
| 실패 | 확정적 검사(허용가격·수수료·레버리지·유지증거금)에 걸리면 효과 없이 소모. 증가 요청은 마진을 환불하되 **실패 수수료** — 예약 노셔널에 대한 풀 개설 수수료, 최소 `FAILED_INCREASE_FEE_BPS`(0.1%) — 를 떼어 LP·프로토콜로 나눕니다. 승인 뒤 현물이 TWAP 을 앞지르면 허용가 초과 실패가 요청자에게 미리 보이므로, 공짜 실패는 용량을 무료로 잡는 수단이었습니다(2차 리뷰 PoC). 정지 구간 환불엔 수수료가 없습니다 |
| 지급 | 환불·지급을 토큰이 거부하면(블랙리스트 등) 되돌리지 않고 `claimableQuote` 에 적립, `claim(to)` 로 다른 주소로도 받습니다. 예전엔 거부되는 트레이더의 실패 요청이 실행마다 되돌려져 롤만 반복하며 예약 용량을 영구히 잡았습니다(2차 리뷰 PoC) |

- 증가: 롱은 높은 쪽, 숏은 낮은 쪽 마크로 진입하고, **포지션 전체**가 equity 기준 레버리지(마진과 equity 중 작은 값)와 유지증거금을 통과해야 합니다. 청산 대상 포지션을 키우는 일이 막힙니다.
- 감소: 롱은 낮은 쪽, 숏은 높은 쪽 마크로 청산. 부분 감소는 남은 포지션이 유지증거금 위여야 하며, 미달이면 전량 청산만 가능합니다.
- 마진 인출: 불리한 쪽 마크에서 equity·마진 양쪽 기준 레버리지와 유지증거금을 통과해야 합니다 — 낡은 마크나 미실현 이익으로는 빼낼 수 없습니다.
- 마진 추가(`addMargin`)는 가격이 필요 없고 안전만 높이므로 즉시, 정지 중에도 열려 있습니다.
- 청산·펀딩은 현재 마크를 바로 씁니다.
- 늦은 실행 등으로 관측 기록이 64 에포크 넘게 떨어져 있으면 실행자가 `hints` 로 기록 위치를 넘깁니다.

#### 5.2.1.1 정지 구간의 정산
정지 구간 안에 정산되는 요청은 동결 마크와 **정지 중 현물 가격**(스왑이 막혀 정지 내내 같은 값) 중 요청자에게 불리한 쪽으로 정산됩니다. 증가·예치(진입)는 정지 중이거나 정지 구간에 정산되면 언제 실행하든 **가격을 읽지 않고** 환불합니다 — 오라클 풀이 시드된 직후 정지가 오면 동결 마크의 창이 시드 이전까지 거슬러 올라가, 가격을 읽으려던 예치는 영구히 실행할 수 없었습니다(2차 리뷰 PoC). 동결 마크만 쓰던 때는 정지 직전에 폭락이 오면, 정지 후 요청한 청산이 폭락 전 가격(요청 시점에 이미 공개된 가격)을 받았습니다 (리뷰 PoC: −21% 폭락 후 롱이 840 대신 4,878 수령).

#### 5.2.2 LP 지분 가격
| | 평가식 | 마크 |
|---|---|---|
| 예치 | `TL − 미실현PnL + 미정산 펀딩` (전체 시가평가) | 금고를 가장 높게 평가하는 정산 마크 |
| 인출 | `TL − max(0, 롱PnL) − max(0, 숏PnL)` (트레이더 손실·미정산 펀딩 불인정) | 금고를 가장 낮게 평가하는 정산 마크 |

예치는 금고의 장부상 이익까지 값을 치르고, 인출은 마진을 넘는 손실(회수 불가)을 LP 지분으로 쳐주지 않습니다. 예전엔 마크가 0 인 순간 예치하면 트레이더 손실을 공짜로 가져갔고, 정지 중엔 악성부채를 이익으로 계산한 가격에 먼저 빠져나갈 수 있었습니다.

인출 후 남은 equity 는 **순노출**(|롱 − 숏|, 승인 대기 중인 증가 포함)이 사용률 상한 이내, **총노출**(큰 쪽)이 그 2배 이내여야 합니다. LP 예치는 오라클 풀이 시드된 뒤에만 요청할 수 있습니다(정산 창에 가격이 반드시 있도록). 쪽별 상한만 보던 때는 펀딩 0 인 롱·숏 동시 포지션으로 양쪽 상한을 채워 LP 출금을 무기한 막을 수 있었습니다. 대기 예약은 금고가 승인 때 약속한 노출이라 빼지 않습니다 — 빼면 승인과 체결 사이에 LP 가 먼저 빠져나가 남은 LP 가 상한의 몇 배를 떠안습니다(2차 리뷰 PoC: 상한 0.8배 → 7배 초과).

#### 5.2.3 펀딩
펀딩은 현재 마크로 누적하고, 마크가 없으면 누적도 시계도 멈춥니다 (나중에 마크가 생기면 그 구간을 온전히 청구). 예전엔 1시간 넘게 쉰 뒤 poke 가 마크를 0 으로 만든 직후 펀딩을 계산해 그동안의 펀딩이 사라졌습니다.
- **수수료 정책: 현물 풀과 동일** — 풀 생성자가 `lpFeeRate` 선택 + 그 `lpFeeRate` 의 **0.1% 가 프로토콜 수수료**, 99.9% 가 LP 로 분배.

### 5.3 현물 ↔ 선물 풀 관계
| 항목 | 현물 풀 | 선물 풀 |
|---|---|---|
| 용도 | 즉시 스왑 | 레버리지 포지션 |
| 가격 결정 | reserves 비 (x*y=k) | 현물 풀 TWAP 마크, 요청 이후 창으로 정산 |
| 같은 `Pair` 소속 | ✅ | ✅ |
| 수수료 설정 | **풀 생성자가 `lpFeeRate` 선택** (그 중 0.1% 가 프로토콜, 99.9% 가 LP) | **현물과 동일** (생성자 선택 + lpFee 의 0.1% 가 프로토콜) |
| LP / 트레이더 | LP (유동성 공급) | 트레이더 (포지션 진입) |

### 5.4 LP 포지션 표현 — ERC-721

> **원칙:** 풀은 **대체가능 LP 토큰을 발행하지 않습니다.** 양도 가능한 유일한 유동성 포지션 표현은 NFT 입니다.

- **풀 내부:** 현물/선물 풀 모두 `sharesOf(address)` / `totalShares()` 라는 **전송 불가 지분 원장**만 유지합니다. `transfer` / `approve` / `allowance` / `totalSupply` 등 ERC-20 인터페이스는 존재하지 않습니다.
- **소유권:** `DexPositionManager` 가 풀의 지분을 수탁하고 ERC-721 을 발행합니다. `positions[tokenId] = {pool, isSpot, liquidity}`. **NFT 전송 = 인출 권한 전송.**
- **구조적 근거:** Uniswap V3 와 동일한 분리 — core 풀은 포지션 원장만 갖고, 토큰화는 periphery 가 담당합니다. 풀 코드는 불변으로 유지되고 매니저는 교체 가능합니다.
- **수수료 수취:** 별도 `collect()` 가 없습니다. 현물은 reserves 에, 선물은 `totalLiquidity` 에 수수료가 자동 복리되므로 지분 가치 상승으로 누적됩니다.
- **메타데이터:** `tokenURI` 가 base64 JSON + base64 SVG 를 **완전 온체인**으로 생성합니다. IPFS 핀·메타데이터 서버·별도 렌더러 컨트랙트가 없습니다. 카드에는 포지션 수명 동안 고정된 값(페어·풀 종류·수수료·풀 주소·토큰 ID)만 표기하며, 가변값인 지분 수량은 마켓플레이스 이미지 캐시로 인해 의도적으로 제외합니다.
- **직접 공급 — 열어 둡니다 (결정됨):** 매니저를 우회해 풀에 직접 유동성을 공급하는 것은 **의도적으로 허용**합니다. 이 경우 **전송 불가한 원장 지분**만 얻으므로, "대체가능 LP 토큰 없음" 원칙은 그대로 유지됩니다.
  - **막지 않는 이유:** 풀에 `onlyPositionManager` 를 걸려면 매니저 주소가 풀에 `immutable` 로 박혀야 합니다(레지스트리 → 팩토리 → 풀). 풀은 관리자·일시정지·업그레이드가 없으므로, **매니저에 버그가 생기면 그 이후 배포된 모든 풀의 유동성이 영구히 잠깁니다.** 비가역적 리스크를 순수성과 맞바꾸지 않습니다.
  - **얻는 것:** core 가 열려 있으므로 매니저는 언제든 교체·병존 가능합니다. Uniswap V3 가 periphery 를 갈아끼울 수 있는 것과 같은 이유입니다.
  - 검증: `test_directPoolLpHasNonTransferableShares` — 우회 공급 시 지분은 받되 전송 경로가 없고 타인이 인출할 수 없음을 고정.

| 항목 | 방식 |
|---|---|
| 풀의 지분 원장 | `sharesOf` / `totalShares` (전송 불가) |
| 양도 가능 표현 | `DexPositionManager` ERC-721 (`S9-POS`) |
| 수수료 정산 | 자동 복리 (지분 가치) — `collect()` 없음 |
| 메타데이터 | 온체인 SVG, 외부 의존성 0 |

## 6. 수수료 (Fee) — 정규 티어 + 커스텀 슬롯, 프로토콜 컷(0.1% of lpFee)

> **원칙 1:** 수수료는 풀 생성자가 고릅니다. 다만 **정규 티어 4개는 항상 열려 있고**, 그 밖의 값은 페어당 **커스텀 슬롯 12개**를 나눠 씁니다.
> **원칙 2:** 설정된 `lpFeeRate` 의 **0.1%** 가 **프로토콜 수수료**로 프로토콜 금고(`ProtocolTreasury`) 에 회수됩니다. 나머지 99.9% 는 LP 에게 분배됩니다.

### 6.1 현물 풀의 수수료율 — 왜 캡이 있나
현물 풀은 **수수료율당 1개**입니다. 무제한이면 매칭 루프가 순회할 풀이 무한정 늘어나므로 상한이 필요한데, 단순한 총량 캡은 **페어를 영구히 망가뜨리는 수단**이 됩니다: 공격자가 쓰레기 수수료로 빈 풀을 캡만큼 찍으면 아무도 쓸만한 티어를 못 만들고, `createPair` 는 재실행이 불가합니다.

그래서 캡을 둘로 나눕니다.

| 구분 | 값 | 성질 |
|---|---|---|
| 정규 티어 | `100` / `500` / `3000` / `10000` ppm (0.01% / 0.05% / 0.30% / 1.00%) | 캡 면제. **항상 생성 가능** |
| 커스텀 티어 | 그 밖의 `1` ~ `10000` ppm | 페어당 12슬롯 (`MAX_CUSTOM_SPOT_POOLS`) |

정규 티어는 선점당해도 무해합니다 — 선점자가 만든 풀이 곧 그 티어의 정식 풀이고, 아무나 유동성을 넣고 라우팅할 수 있습니다. 커스텀 슬롯이 전부 소진돼도 정규 4개가 남으므로 페어는 계속 쓸 수 있습니다.
- 조회: `Pair.isCanonicalFeeTier(ppm)`, `Pair.customSpotPools()`.
- 회귀 테스트: `test/PairGrief.t.sol`.

### 6.2 적용 범위
- **현물 풀:** `Pair.createSpotPool(lpFeeRatePpm)`.
- **선물 풀:** `Pair.createPerpPool(...)` — 범위는 `1` ~ `10000` ppm 으로 동일하되, 슬롯 캡은 없습니다. 선물은 `quoteToken` 별로 중복만 막으며, 소진시킬 총량 상한이 없어 그리프 대상이 아닙니다.
- **시장가/지정가 주문:** 거래가 라우팅되는 **해당 풀의 `lpFeeRate`** 가 자동 적용. 단 **책 직접 체결에는 풀 수수료가 붙지 않습니다** (§4.2).

### 6.3 수수료 분배 구조
거래 1회당 차감되는 총 수수료 = `lpFeeRate` (거래량 대비). 그 안에서:
- **프로토콜 수수료** = `lpFeeRate × 0.1%` (= `lpFeeRate × 0.001`) → `ProtocolTreasury`
- **LP 수수료** = `lpFeeRate × 99.9%` (= `lpFeeRate × 0.999`) → 해당 풀의 LP

| 구분 | 비율 | 수취자 |
|---|---|---|
| **프로토콜 수수료** | `lpFeeRate` 의 **0.1%** (= `lpFeeRate × 0.001`) | **프로토콜 금고 (`ProtocolTreasury`)** |
| LP 수수료 | `lpFeeRate` 의 **99.9%** (= `lpFeeRate × 0.999`) | 해당 풀의 LP |
| **총 수수료** | `lpFeeRate` | — |

#### 예시
| `lpFeeRate` (풀 생성자 설정) | 프로토콜 (0.1% of lpFee) | LP (99.9% of lpFee) |
|---|---|---|
| 0.10% (10 bps) | 0.0001% (0.01 bps) | 0.0999% (9.99 bps) |
| 0.30% (30 bps) | 0.0003% (0.03 bps) | 0.2997% (29.97 bps) |
| 1.00% (100 bps) | 0.0010% (0.10 bps) | 0.9990% (99.90 bps) |

### 6.4 LP 수수료 분배
- 분배 정책은 설정값이 아니라 고정입니다 (`FeeSplit`): 프로토콜 0.1%, LP 99.9%. `feeRecipient` 같은 풀별 노브는 없습니다.
- LP 몫은 별도 인출 없이 복리됩니다 — 현물은 reserves 에, 선물은 `totalLiquidity` 에 남습니다 (§5.4).
- 프로토콜 몫은 풀에 적립되며 `collectProtocolFees()` 로 누구나 금고에 쓸어 넣을 수 있습니다.

### 6.5 반올림
총 수수료와 프로토콜 몫 모두 **올림**입니다 (`FeeSplit`). 내림이면 수수료가 0 이 될 만큼 작게 쪼갠 거래는 수수료를 안 냈고, 수수료가 1000 단위 미만인 거래마다 프로토콜 몫이 0 이었습니다 (0.01% 풀의 0.1 BTC 미만 WBTC 스왑 전부). 올림은 거래당 최대 1 단위, 항상 거래자 쪽으로 움직입니다. `SpotPool.getAmountIn` 은 이 반올림에서 정확히 최소 입력을 돌려줍니다.

### 6.6 제약
- **프로토콜 컷 비율 (0.1%):** 하드코딩. 거버넌스 노브 없음 (`FeeSplit.PROTOCOL_CUT_DIVISOR`).
- **`lpFeeRate` 범위:** `1` ~ `10000` ppm = **0.0001% ~ 1%**. 하드코딩이며 owner 권한으로 바꿀 수 없습니다 (`MIN_LP_FEE_PPM` / `MAX_LP_FEE_PPM`).
- 풀의 **총 수수료**는 `lpFeeRate` 그대로이고, 그 내부에서 0.1% / 99.9% 로 갈립니다.

## 8. 비상 정지 (Emergency Pause)

> **원칙: 진입만 막고, 출구는 어떤 상태에서도 열어 둡니다.** 자금을 가두는 정지는 정지가 없는 것보다 나쁩니다.

플래그는 `DexRegistry.paused` 하나이며, 모든 풀과 페어가 그것을 읽습니다. 풀에는 owner·업그레이드·자체 저장공간이 없지만 이미 `registry` 주소를 immutable 로 들고 있으므로, 레지스트리를 경유하면 **풀 배포 방식을 바꾸지 않고** 이미 배포된 풀에도 적용됩니다 (`libraries/Pausing.sol`).

### 8.1 권한
| 동작 | 권한자 |
|---|---|
| `pause()` | guardian, emergencyAdmin(Safe), owner(타임락) |
| `unpause()` | emergencyAdmin(Safe) 또는 owner |
| `setGuardian(addr)` | emergencyAdmin(Safe) 또는 owner (`address(0)` 이면 빠른 경로 해제) |
| `setEmergencyAdmin(addr)` | owner(타임락) 전용 |

guardian 은 **멈추는 것만** 가능하고 그 외 권한이 없습니다. Safe 는 사고 진행 중에 서명을 모으기엔 느립니다. 재가동은 신중해야 할 행위이므로 빠른 키에 두지 않습니다. owner(타임락)도 모든 하위 권한을 가지므로 Safe 키를 잃어도 지연 후 복구할 수 있습니다.

### 8.2 범위
| 막힘 (진입) | 열림 (탈출·정리) |
|---|---|
| `SpotPool.swapExactIn` / `swapFromPair` | `SpotPool.removeLiquidity` |
| `SpotPool.addLiquidity` | `PerpPool.requestWithdraw` / `executeLp` (인출) |
| `PerpPool.requestDeposit` / `requestIncrease` | `PerpPool.requestDecrease` / `requestRemoveMargin` / `executeOrder` |
| 정지 중 정산되는 증가·예치 요청 (실행 시 환불) | `PerpPool.addMargin` / `updateFunding` |
| `PerpPool.liquidate` (§8.3) | `Pair.cancelOrder` / `removeExpired` / `claim` |
| `Pair.placeOrder` / `matchOrders` / `matchFromPool` | `collectProtocolFees` / `SpotPool.skim` |
| `Pair.createSpotPool` / `createPerpPool` | `DexPositionManager.decrease*` / `settlePerp` / `burn` |

매칭은 거래를 실행하므로 진입으로 분류합니다. 정지 중 메이커의 출구는 `cancelOrder` 입니다.

`DexRouter` 와 `DexPositionManager` 에는 별도 검사가 없습니다 — 진입 경로가 결국 풀을 호출하므로 거기서 되돌려지고, 출구 경로는 어차피 열려 있어야 합니다.

### 8.3 정지 중 마크 동결
정지 중엔 스왑이 막혀 현물 가격을 차익거래로 되돌릴 수 없습니다. 마크가 계속 굴러가면 정지 직전의 (조작됐을 수 있는) 가격이 그대로 오라클에 박힙니다. 그래서 **정지 중 마크는 정지 직전 경계에서 동결**되고, 정지 구간 안에 정산되는 요청은 언제 실행하든 동결 마크로 정산됩니다 (정지 중 실행과 해제 후 실행이 "이미 아는 두 가격 중 고르기" 가 되지 않게). 탈출(감소·인출)은 동결 마크로 계속 가능하고, 증가·예치는 환불됩니다.

정지 해제 직후 `MARK_WINDOW + 60초` 동안은 마크 창에 정지 구간 가격이 섞여 있으므로 청산을 막습니다. 트레이더는 정지 중에도 `addMargin` 으로 미리 보충할 수 있습니다.

### 8.4 청산은 왜 막는가
대부분의 선물 설계와 반대되는 선택입니다. 정지를 누를 가장 그럴듯한 이유가 **마크 가격 이상**인데, 잘못된 마크로 청산을 돌리면 멀쩡한 트레이더의 담보가 **되돌릴 수 없게** 넘어갑니다. 방치된 악성부채는 금고가 흡수하고 나중에 풀 수 있는 회계 손실이지만, 부당 청산은 복구가 불가능합니다.

### 8.5 만료 타이머가 없는 이유
출구가 항상 열려 있으므로 Safe 키를 분실해 영구 정지 상태가 되더라도 **자금은 갇히지 않습니다.** 새 진입만 불가능해집니다. 그 보장이 만료 타이머보다 강하므로 타이머를 두지 않습니다.

검증: `test/Pause.t.sol` — 특히 `testPauseNeverTrapsFunds` 가 정지 상태에서 주문 취소·포지션 청산·양쪽 풀 LP 인출이 모두 가능함을 고정합니다.

## 9. 마진 격리 (Isolated Margin) — 확정

> **결정: 포지션 증거금은 풀별·방향별로 격리합니다.** `positions[trader][isLong].marginQuote`.
> 크로스 마진은 미구현이 아니라 **의도적으로 채택하지 않은** 설계이며, 로드맵에도 없습니다 (§9.3).

### 9.1 크로스가 주는 것과 뺏는 것
크로스 마진은 기능 공백을 메우는 게 아니라 **자본 효율 최적화**입니다. 격리로도 여러 시장에 동시 포지션을 들 수 있고, 증거금을 각각 넣을 뿐입니다 — 크로스가 없어서 불가능해지는 동작은 없습니다.

그리고 그 이득은 **한 계정이 동시에 들고 있는 시장 수에 비례**합니다.

| 같은 quoteToken 기준 perp 시장 수 | 크로스의 이득 |
|---|---|
| 1 | 정확히 0 — 교차할 상대가 없음 |
| 2~3 | 미미 |
| 수십 | 비로소 유의미 |

대신 잃는 것은 **봉쇄(containment)** 입니다. 지금은 어느 풀의 마크가 틀려도 피해가 그 풀에 갇힙니다. 크로스에서는 연결된 **아무 시장**의 마크 오류가 멀쩡한 시장의 포지션까지 잘못 청산시킵니다. 이는 §8.3 에서 "정지 중 청산 차단"을 택한 근거(잘못된 마크로 인한 청산은 비가역적)와 정확히 같은 축이며, 크로스는 그 표면을 시장 수만큼 넓힙니다. 풀에는 owner 도 업그레이드도 없으므로 되돌릴 수단이 없습니다.

격리 전용이 실격 사유는 아닙니다 — GMX 는 포지션별 격리로 최대 규모 perp DEX 중 하나가 됐습니다. 크로스가 업계 표준인 것은 맞지만(dYdX v4, Hyperliquid 등) 진입 요건은 아닙니다.

### 9.2 구현했다면 깨졌을 것들
| 항목 | 영향 |
|---|---|
| 풀 단독 감사성 | 증거금이 풀 밖으로 나가면 `quote balance == totalLiquidity + sum(margins) + protocolFeesQuote` 가 성립하지 않습니다 |
| 청산 | `_belowMaintenance` 가 마크 하나를 씁니다. 크로스면 N개 풀의 N개 마크로 계정 전체 equity 를 계산해야 하고, 가스가 포지션 수에 비례하며 부분청산 순서 정책이 새로 필요합니다 |
| 악성부채 귀속 | 지금은 각 풀 금고가 자기 손실을 먹습니다. 계정이 여러 시장에 걸쳐 마이너스면 어느 풀 LP 가 먹는지에 정답이 없습니다 |
| 펀딩 정산 | `_settleFunding` 이 풀 내부 이동에서 계정↔풀 간 호출로 바뀌고, 잔액 부족 시 지급 순서 문제가 생깁니다 |
| quoteToken 경계 | 담보가 다르면 그 사이 가격 오라클이 또 필요하므로, 결국 같은 토큰 안에서만 크로스됩니다 |

`maxUtilizationBps` 는 **풀 LP 노출** 기준이므로 크로스에서도 그대로 동작합니다.

### 9.3 로드맵에 없음 — 그리고 그게 감사 제약을 없앰
크로스 마진은 **추가 계획이 없습니다.** 조건부 보류가 아니라 최종 결정입니다.

이 결정이 실무적으로 갖는 값은 **감사 일정이 자유로워진다**는 것입니다. 격리를 전제로 감사받은 뒤 크로스를 얹으면 증거금 회계 · 청산 · 악성부채 경로가 전부 바뀌어 감사 결과의 상당 부분이 무효가 됩니다. "나중에 할 수도 있다" 를 열어두는 한 감사는 그 결정을 기다려야 하지만, 닫아두면 지금 상태로 감사에 들어갈 수 있습니다.

바꾸고 싶어지면 그때 변경 이력에 뒤집는 항목을 추가하고 **감사를 다시** 받는 것이 순서입니다. 되돌릴 수 없는 건 결정이 아니라 배포된 컨트랙트이므로(§9.1), 결정 자체는 문서에서 뒤집을 수 있습니다.

### 9.4 더 싼 중간 단계
자본 효율 대신 **사용성**만 원한다면, 봉쇄를 깨지 않고 얻을 수 있는 선택지가 있습니다.

- **공유 입금 + 격리 리스크** — 주변부 컨트랙트에서 한 번 입금·승인하고 여러 풀에 배분. 배분된 증거금은 여전히 각 풀이 보유하므로 위 불변식이 유지됩니다. 풀 코드 무변경이라 **이미 배포된 풀에도 적용 가능**합니다.
- **같은 풀 내 롱/숏 네팅** — 헤지 포지션이 한쪽 다리만으로 청산되지 않게 합니다. 마크를 하나만 읽으므로 크로스의 위험이 없습니다.

둘 다 미구현이며, 필요해질 때 개별로 판단합니다.

## 10. 금고 인출 정책 (Treasury Withdrawals)

> **결정: `ProtocolTreasury` 의 owner 는 Safe 가 아니라 `TimelockController` 입니다.**

### 10.1 왜 타임락인가
금고가 털리는 시나리오는 사실상 **Safe 키 침해** 하나이고, owner 가 Safe 면 그 순간 **즉시 전액**이 나갑니다. 아무도 관측하거나 대응할 시간이 없습니다.

여기에 유용한 비대칭이 있습니다.

| | 즉시성이 필요한가 |
|---|---|
| `pause` | **필수** — 그래서 guardian 이라는 빠른 단일 키를 둡니다 (§8.1) |
| 금고 인출 | **전혀 불필요** — 수수료를 급히 빼야 할 이유가 없습니다 |

정지에 지연을 걸면 치명적이지만 금고에는 무해합니다. 그래서 타임락은 **비용이 거의 0 인 방어책**입니다. 목적지 화이트리스트나 주기 한도는 채택하지 않았습니다 — 타임락이 주는 관측 시간이 같은 목적을 달성하면서 운영 마찰과 추가 권한을 만들지 않습니다.

### 10.2 역할 구성
| 역할 | 보유자 | 비고 |
|---|---|---|
| PROPOSER | Safe | 인출·업그레이드를 큐에 올림 |
| CANCELLER | Safe, **guardian** | 아래 참조 |
| EXECUTOR | **개방** (`address(0)`) | 지연이 지나면 누구나 실행. Safe 가 자기 자금에서 검열당할 수 없음 |
| DEFAULT_ADMIN | **타임락 자신만** | 역할 변경도 지연을 거침 |

**guardian 이 canceller 인 것이 핵심입니다.** 정지용으로 이미 존재하는 빠른 키가, 침해된 Safe 가 올린 드레인 제안을 만료 전에 취소할 수 있습니다. 타임락이 자기 자신만 admin 이므로 그 canceller 권한을 지연 없이 빼앗을 수 없고, 빼앗으려는 제안 자체도 guardian 이 취소할 수 있습니다.

기본 지연은 **48시간**(`TREASURY_TIMELOCK_DELAY` 로 조정, 배포 후에는 타임락 스스로 변경). 금고 **업그레이드**(`_authorizeUpgrade`)도 같은 owner 이므로 함께 지연 대상입니다 — 악성 업그레이드로 뒷문 인출 함수를 심는 경로를 막습니다.

### 10.3 레지스트리도 타임락 뒤로
예전엔 `DexRegistry` owner 가 Safe 였고, `setFactories` 나 업그레이드 한 번으로 **이미 주문이 쌓인 페어**에 악성 풀을 붙여 오더북 에스크로 전체를 빼낼 수 있었습니다 (감사 PoC: 매도 에스크로 100%, 매수 99.7%). 금고는 48시간 지연으로 보호하면서 그보다 큰 에스크로가 즉시 노출돼 있던 셈입니다. 이제 세 겹으로 막습니다.

1. **레지스트리 owner = 같은 타임락.** 업그레이드·팩토리 변경이 48시간 지연을 거치고 guardian 이 취소할 수 있습니다.
2. **권한 분리.** 즉시성이 본질인 `unpause`·`setGuardian` 은 `emergencyAdmin`(Safe)에게 따로 둡니다. owner 는 이 둘도 할 수 있어 Safe 를 잃으면 지연 후 복구합니다.
3. **페어가 현물 팩토리를 배포 시점 값으로 고정**합니다 (`Pair.spotPoolFactory` immutable). 현물 팩토리 변경은 이후 생성되는 페어에만 닿습니다. 게다가 페어는 풀의 반환값을 믿지 않고 잔고 변화로 검증하므로(§4.2) 악성 풀이 붙어도 에스크로를 빼낼 수 없습니다. 선물 팩토리는 페어 에스크로와 무관하므로 생성 시점에 레지스트리에서 읽습니다 — 선물이 꺼져 있을 때 만든 페어도 나중에 선물을 붙일 수 있게.

남는 신뢰 (모두 타임락 지연과 guardian 취소가 막는 범위):
- 레지스트리 업그레이드가 `isSpotPool` 을 바꾸면 주변부(Router/PositionManager)가 가짜 풀을 진짜로 볼 수 있습니다.
- 선물 풀은 정지 상태(`pauseWindow`)를 레지스트리에서 읽어 정산 경계를 정합니다. 악성 업그레이드는 정산 가격 경계를 바꾸거나 `pauseWindow` 를 되돌려 선물 출구를 멈출 수 있습니다.
- 새 선물 풀은 그 시점의 선물 팩토리에서 나옵니다.

#### guardian 거부권의 대가
guardian 은 자기 canceller 권한을 빼앗는 제안도 취소할 수 있습니다. 침해된 Safe 를 막는 장치이지만, 반대로 **guardian 키가 털리면** 금고 인출과 레지스트리 업그레이드에 영구 거부권이 생깁니다 (자금이 빠져나가지는 않음). 의도된 맞교환이므로 유지하되, 운영 조건을 둡니다:
- guardian 키는 Safe 서명자와 **다른 키** (배포 워크플로가 메인넷에서 거부).
- Safe 는 n-of-n 이 아닌 구성 (예: 2-of-3). n-of-n 이면 키 하나 분실로 재가동·guardian 교체·모든 타임락 제안이 영구히 불가능해집니다 (워크플로 경고).

검증: `test/TreasuryTimelock.t.sol` — Safe 단독 인출 차단, 지연 미경과 실행 실패, guardian 의 큐 취소, canceller 박탈 불가, 관리자 부재, 레지스트리 업그레이드·팩토리 변경의 지연과 취소, Safe 의 즉시 재가동. `test/DexRegistry.t.sol` — 팩토리 변경이 기존 페어에 닿지 않음, 역할 분리.

## 11. 알려진 한계

- **키퍼 의존:** 요청은 정산 에포크(60초) 안에 실행돼야 그 가격을 받습니다. 놓쳐도 요청자에게만 불리하지만, 사용성을 위해 실행 수수료를 받는 키퍼(또는 프로토콜 키퍼)가 필요합니다.
- **긴 정지:** 정지 중 청산·인출은 정지 직전 가격들로 정산됩니다. 외부 시장이 크게 움직이는 긴 정지 동안엔 낡은 가격으로 빠져나가는 선택이 생깁니다. 정지는 짧게 유지하는 운영이 전제입니다.
- **연속 정지:** 레지스트리는 마지막 정지 구간만 기억합니다. 정산 에포크가 이전 정지 구간에 있던 요청이 다음 정지 이후 실행되면 동결 처리가 빠집니다(롤된 요청은 불리한 가격만 더해지므로 영향 제한적).
- **차익거래 없는 토큰:** 외부 차익거래가 없는 풀은 가격 자체를 공격자가 정할 수 있어, 어떤 TWAP 오라클 선물도 안전하지 않습니다. 깊이 상한은 비용을 올릴 뿐입니다.
- **오라클 깊이 이탈·대여:** `DEPTH_WINDOW`(1시간)보다 오래 넣어 둔 깊이는 승인에 그대로 인정되고, 포지션을 연 뒤 오라클 풀 유동성이 빠지면 기존 포지션은 얇은 오라클에 남습니다 (2차 리뷰 PoC: 100배 깊이를 1시간 6분 유지 → 약 4k 깊이 오라클에 60k 개설). 얇아진 뒤의 정산은 창 직전 55분 TWAP 과의 최악값이고 깊이가 조화평균이라 창을 밀거나 창 일부만 빼고 미는 조작은 막히지만, 창의 대부분(R2-3 수치로 약 95%)을 깊게 두고 몇 초만 빼서 미는 조작은 그 시간 비율만큼 TWAP 를 움직이고, 55분 내내 가격을 붙잡아 두는 조작도 막지 못합니다 — 둘 다 차익거래가 활발하면 비쌉니다. 반대로 얇은 동안엔 정직한 요청도 두 가격 중 불리한 쪽을 받고(추세장에서 손해), 오라클 풀의 큰 LP 는 유동성을 빼서 이 상태를 만들 수 있습니다. 깊고 차익거래가 활발한 오라클 풀을 고르는 것이 전제입니다.
- **조화평균의 대가 — 순간 이탈:** 오라클 풀 유동성의 99% 이상을 가진 LP 가 전부 뺐다가 다음 블록에 다시 넣기만 해도, 그 1초가 조화평균을 지배해 **1시간 동안 신규 포지션 승인이 막히고** 그 창의 정산은 최악값으로 처리됩니다 (2차 리뷰 PoC: 400k 깊이 풀에서 400 노셔널도 50분 뒤까지 `OracleTooShallow`). 지분이 99% 아래면 영향은 미미합니다. 단독 LP 가 유동성을 옮길 땐 **새 유동성을 먼저 넣고 기존 것을 빼야** 합니다. 지배적 LP 는 어차피 유동성을 빼서 승인을 막을 수 있으므로 새 권한은 아니며, 산술·기하평균은 창 일부만 얇게 하는 조작에 약해(허용되는 얇은 구간 ~4% → ~35% 이상) 택하지 않았습니다. 오라클 풀의 유동성이 한 LP 에 몰리지 않는 것도 전제입니다.
- **사용률 초과 가능:** 승인은 요청 시점 마크 기준이라, 체결가가 승인 마크보다 불리하게 움직이면 실행 후 노출이 상한을 잠시 넘을 수 있습니다. 대기 예약은 인출 검사에 들어가므로 LP 인출로는 넘지 않습니다.
- **정지 직전 가격:** 정지 중 현물가는 정지가 걸린 순간 풀에 남은 가격입니다. guardian 의 `pause()` 를 앞질러 스왑하면 그 값을 정할 수 있고, 정지 구간에 정산되는 탈출·인출(정지 약 6분 전까지 요청된 것 포함)이 동결 마크와의 최악값으로 그 값을 받습니다. 금고에 불리한 쪽으로는 쓸 수 없지만(최악값) 탈출하는 쪽은 손해를 볼 수 있습니다.
- **대기 중 마진 추가 불가:** 요청(감소·마진 인출 포함)이 대기 중인 쪽엔 약 6분간 `addMargin` 이 막히고 청산은 열려 있습니다. 부분 청산 요청 전에 미리 보충해야 합니다.
- **정직한 실패도 수수료:** 실패 수수료는 실패 이유를 가리지 않습니다. 가격이 허용가를 넘거나 체결가에서 레버리지·유지증거금을 통과하지 못한 증가 요청도, 일부러 실패시킨 요청과 구별할 수 없으므로 같은 수수료를 냅니다.
- **대기 증가가 인출을 막음:** 같은 이유로 누구든 증가 요청으로 다른 LP 의 인출을 실패시킬 수 있고, LP 가 정산 가격을 본 뒤 자기 인출을 이렇게 무를 수도 있습니다. 비용은 실패 수수료(예약 노셔널의 0.1% 이상) 또는 실제 포지션이고, 막힌 인출은 지분을 돌려받아 다시 요청합니다.
- **작은 주문 정리:** 잔량이 `DUST_UNITS`(1e4 원시 단위) 미만인 주문은 풀 반올림에 지면 닫힐 수 있습니다(WBTC $60k 기준 약 $6 미만). 그 이상은 기다리며, 풀이 지정가 근처 몇 bp 안에 머무는 동안은 그 가격대의 풀 체결이 멈춥니다.
- **레지스트리 크기:** `DexRegistry` 는 `Pair` 생성 코드를 품어 24KB 한도까지 ~780바이트 남았습니다(Monad 자체 한도는 더 크지만 테스트 환경 기준).
